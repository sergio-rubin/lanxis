# Protocolo LANXIS

Versión inicial: `1`. La comunicación experimental funciona en red local autorizada. `GET /health` devuelve versión y capacidades; `POST /register` acepta `{"client_id":"..."}` con el encabezado `X-Lanxis-Code` de seis dígitos y registra clientes únicos en la sesión del servidor; `GET /ping` devuelve JSON pequeño con ID de petición y tiempo UTC; `GET /download?bytes=N` transmite bloques deterministas generados sin cargar el total en memoria; `POST /upload?bytes=N` recibe bloques deterministas y confirma el tamaño y la integridad. El cliente verifica el ID y versión del ping, y byte por byte las transferencias antes de marcarlas como válidas. La clave se genera de nuevo al iniciar el servidor.

El servidor escucha consultas UDP `LANXIS_DISCOVER_V1` en el puerto 8041 y responde JSON con nombre, versión y puerto HTTP. Los broadcasts pueden bloquearse por firewall o aislamiento de clientes; la URL manual sigue disponible. El descubrimiento no divulga el código de emparejamiento.

El puerto, tamaño de carga, concurrencia y timeout son configurables con límites explícitos. HTTP RTT no es ICMP ping. La transferencia registra por separado bytes realmente enviados y recibidos y usa el tiempo monotónico local para calcular throughput efectivo según la dirección. Una ejecución individual no puede etiquetarse como E4–E6 ni registrar más de un cliente.

El motor TCP abre un puerto efímero adicional, publicado como `tcp_port` en `/health` junto a la capacidad `tcp-transfer`. El cliente escribe una línea ASCII `LANXIS/1 <código> <uuid> <download|upload> <bytes>\n`. El servidor verifica el código, el identificador, el tamaño (0–100 MiB; subida > 0) y un máximo de cuatro transferencias activas. Responde `OK <uuid> <bytes>\n` y transmite o recibe un patrón determinista de bloques de 64 KiB generado por streaming. El cliente compara el UUID y todos los bytes antes de marcar éxito. La conexión y transferencia completas se cronometran con `Stopwatch`; el resultado se etiqueta `tcp`, separado de la latencia HTTP. Si el puerto adicional no está disponible, `/health` no anuncia TCP y HTTP sigue operativo. Esta ruta se probó en loopback, no en dispositivos físicos.

El motor de eco UDP usa otro puerto efímero anunciado como `udp_port` y `udp-echo`. Cada datagrama contiene `LANXIS/1 <código> <uuid>\n` y 0–1024 bytes de carga determinista. El servidor solo devuelve datagramas autenticados de tamaño limitado y nunca responde con más bytes de los recibidos. El cliente verifica el puerto, la dirección y todo el contenido; cada timeout se conserva como una medición fallida. Sus bytes enviados incluyen encabezado y carga, y no se calcula throughput a partir de un único RTT. Las peticiones se envían secuencialmente: esta versión observa ausencia de eco, pero todavía no mide reordenamiento entre datagramas simultáneos. Esta ruta se probó en loopback, no en dispositivos físicos.

Para ensayos coordinados, cada participante registra un `client_id` persistente y consulta `GET /work?client_id=...` cada 500 ms. El servidor publica un trabajo con parámetros y marcas UTC para una barrera inicial aproximada. Cada cliente ejecuta las solicitudes con su propio reloj monotónico, guarda una copia local y coloca lotes de hasta 100 muestras en un outbox SQLite antes de enviarlos por `POST /result`; la clave de emparejamiento protege ambas rutas. Los lotes se reintentan, se conservan tras reiniciar la app y el servidor deduplica `request_id`. Un mensaje `complete` cierra la participación. El servidor marca el ensayo incompleto si no recibe `n × clientes` observaciones y admite reenvíos tardíos de hasta 32 ensayos en memoria para recuperar un ensayo incompleto. Tras reiniciar el servidor, los trabajos anteriores ya no están disponibles y los lotes locales quedan visibles como pendientes. Este protocolo ha sido probado con dos instancias en loopback; la sincronización de reloj y la interoperabilidad física siguen pendientes de medición.
