# Soporte por plataforma

| Capacidad | Android | Windows | Linux |
| --- | --- | --- | --- |
| Flutter nativo | Objetivo | Objetivo | Objetivo |
| Servidor/cliente HTTP, transferencia TCP y eco UDP por LAN existente | Implementación compartida | Implementación compartida | Implementación compartida |
| SQLite local | Implementación compartida | Implementación compartida | Implementación compartida |
| Distancia automática al punto de acceso | Wi-Fi RTT mediante API oficial cuando el equipo, el punto de acceso y los permisos lo permiten; con incertidumbre y procedencia | Sin medición automática implementada | Sin medición automática implementada |
| Distancia estimada entre pares por BLE | Baliza y escáner LANXIS, RSSI repetido y margen orientativo; requiere Bluetooth y permisos | Baliza y escáner BLE pendientes | Baliza y escáner BlueZ mediante D-Bus; no usa Bluetooth para las transferencias |
| Hotspot controlado por la app | Adaptador Kotlin `startLocalOnlyHotspot`, sujeto a permisos y fabricante; compilado, pendiente prueba física | Control automático no implementado; «Ajustes Wi-Fi» abre la página oficial de Windows para configurar una red existente | Adaptador `nmcli`/NetworkManager con detección AP, PolicyKit y perfil temporal; compilado, pendiente prueba con hardware |

Estos son objetivos de implementación, no certificaciones generales de hardware. La aplicación muestra las capacidades de red anunciadas por el servidor y mantiene una ruta manual de LAN cuando un adaptador no está disponible. HTTP, TCP y UDP han pasado pruebas de loopback en Linux; las pruebas de red y persistencia pasan también en CI de Windows. En Wi-Fi real se probó Android como servidor y Linux como cliente con 35/35 mediciones válidas. Android también encontró y se registró como cliente de un servidor Linux y completó E1 con 5/5 muestras. Windows en hardware y otras combinaciones están pendientes. El eco UDP actual envía datagramas secuenciales y no informa reordenamiento. Android 17/API 37 requiere revisar `ACCESS_LOCAL_NETWORK` al actualizar el SDK objetivo.

La distancia es opcional. Si el servidor Android o Linux anuncia una baliza BLE, el cliente coteja su identificador con la respuesta HTTP del servidor y estima distancia a partir de varias lecturas RSSI. Es una aproximación sin calibración individual: paredes, orientación y radios pueden producir errores mayores que el margen mostrado. Para un estudio que exija metros precisos, mida y registre la distancia físicamente. Wi-Fi RTT solo se intenta en Android si el servidor coincide con el gateway de la red y el punto de acceso anuncia 802.11mc. Si no existe una ruta medible, se conserva «sin dato»; la distancia objetivo de un escenario no se confunde con una observación. Bluetooth aporta distancia; las transferencias continúan por HTTP/TCP/UDP.
