Estos son objetivos de implementación, no certificaciones generales de hardware. La aplicación muestra las capacidades de red anunciadas por el servidor y mantiene una ruta manual de LAN cuando un adaptador no está disponible. HTTP, TCP y UDP han pasado pruebas de loopback en Linux; las pruebas de red y persistencia pasan también en CI de Windows. En Wi-Fi real se probó Android como servidor y Linux como cliente con 35/35 mediciones válidas. Android también encontró y se registró como cliente de un servidor Linux y completó E1 con 5/5 muestras desde segundo plano. Windows en hardware y otras combinaciones están pendientes. El modo UDP ráfaga registra pérdidas y reordenamiento, probado con respuestas controladas en loopback; falta prueba física. Android 17/API 37 requiere revisar `ACCESS_LOCAL_NETWORK` al actualizar el SDK objetivo.

La distancia es opcional. Si el servidor Android o Linux anuncia una baliza BLE, el cliente coteja su identificador con la respuesta HTTP del servidor y estima distancia a partir de las lecturas RSSI disponibles. Android requiere al menos tres; BlueZ puede entregar una o dos y entonces el resultado se marca «lecturas escasas» con margen mayor. Es una aproximación sin calibración individual: paredes, orientación y radios pueden producir errores mayores que el margen mostrado. Para un estudio que exija metros precisos, mida y registre la distancia físicamente. Wi-Fi RTT solo se intenta en Android si el servidor coincide con el gateway de la red y el punto de acceso anuncia 802.11mc. Si no existe una ruta medible, se conserva «sin dato»; la distancia objetivo de un escenario no se confunde con una observación. Bluetooth aporta distancia; las transferencias continúan por HTTP/TCP/UDP.
